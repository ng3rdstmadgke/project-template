# AIワークフロー

非自明なタスクを進める際の標準ワークフローを定義する。

**工程の省略はこのワークフローの目的の否定である。** 0の適用判断で「非自明」と出たら、1〜7は原則すべて実施する。各工程は指定スキルを**実際に起動**して進め、要約や記憶での代替をしない。

## ワークフロー全体像

| # | 工程 | 使うスキル | 成果物 |
|---|------|-----------|--------|
| 0 | 適用判断 | — | — |
| 1 | 設計 | `/superpowers:brainstorming` `/japanese-tech-writing` | `spec.md` |
| 2 | 実装計画 | `/superpowers:writing-plans` | `task.md` |
| 3 | 設計・計画レビュー(別sub agent) | — | `review.md` |
| 4 | 実装 | `/superpowers:subagent-driven-development` | コード |
| 5 | 実装レビュー(別sub agent) |  | — |
| 6 | ADR記録 | — | `docs/adr/*.md` |
| 7 | 教訓の抽出 | (auto memory) | — |

成果物およびタスクに必要なファイルはすべて `agent-tasks/タスク名/` 配下に置く。`タスク名` はブランチ名のチケットID(例: `198_improve_e2e_test`)に揃え、追跡できるようにする。

## 🚩 Red Flags — 手が滑っているサイン

以下が一つでも当てはまったら**止まって該当工程に戻る**。

- `spec.md` / `task.md` を書かずに実装を始めようとしている
- レビュー(3・5)を、書いた本人(自分)がやろうとしている
- テストを実行せず「たぶん動く」で完了にしようとしている
- 未確認のまま commit / push / deploy しようとしている
- 指定スキルを起動せず、要約や記憶で代替しようとしている

### よくある言い訳と現実

| 言い訳 | 現実 |
|-------|------|
| 「簡単なタスクだから spec/plan は省略」 | 「簡単」に見えるタスクほど前提のズレが手戻りを生む。0で非自明と出たなら1〜6は省略しない |
| 「自分でレビューすれば十分」 | 書いた本人のレビューは盲点を見逃す。3・5のレビューは必ず**別の** sub agent に委ねる |
| 「テストは後で / たぶん動く」 | 動作を実証せずに完了としない。テストを実行しログを確認して**実証**する |
| 「ついでに commit しておく」 | commit・push・deploy は勝手に行わない。2で明示的にユーザー確認を得た場合のみタスクに含める |
| 「brainstorming は読まず自分で設計」 | 各工程は指定スキルを**実際に起動**する。description の要約で代替しない |

## 0. 適用判断

まずタスクの性質を見極め、このワークフローを適用するかを判断すること。

| タスクの性質 | 進め方 |
|------------|--------|
| 非自明(3ステップ以上、または設計判断を伴う) | 本ワークフロー(1〜6)に従う |
| 些細(単純な質問、1ステップの修正など) | 直接対応してよい |

## 1. 設計

`/superpowers:brainstorming` スキルを利用して、開発者と共同で設計を行う。
設計は `agent-tasks/タスク名/spec.md` にマークダウンで保存する。

### 情報収集

設計は正確な情報を前提に行わなければならない。

- 与えられたタスクに必要な情報をリポジトリ内から収集すること
- 外部サービスやライブラリの仕様はContext7もしくはweb検索で最新の情報を取得すること

### ブレインストーミング

- `/superpowers:brainstorming` スキルを利用して、得られた情報を元にユーザーと共同で設計判断を行う
  - UI/UX改善を含む場合は `Visual Companion` を利用すること
- 設計にはテスト戦略を含めること。TDDの要領で正しい動作を事前に定義しておくこと
- デプロイ手順の作成、ドキュメントの修正もスコープに含める
- **設計の基本原則**に従うこと
  - **シンプル第一**: あらゆる変更を可能な限りシンプルにする。コードへの影響を最小限に抑える
  - **最小限の影響**: 必要な箇所だけに手を加える。バグの混入を避ける
  - **怠慢の禁止**: 現在の実装に引きずられたり、一時しのぎの修正を行わない。シニアディベロッパーの基準で長期的に運用・拡張が容易なアーキテクチャを目指すこと
  - **深い洞察**: 表面的な問題の解決を目指すのではなく、問題の根本原因を見つけ、設計レベルでの改善が可能かを常に考えること
  - **普遍的な設計原則への準拠**: Clean Architecture, DDD, TDD, SOLIDの原則, GoFデザインパターンといった普遍的な設計原則に準拠すること

### spec.mdの作成

- `/japanese-tech-writing` スキルの方針に従い、人間とAIどちらも理解しやすいように記述すること
- Mermaid、表、箇条書き、コードブロックを積極的に利用し、構造・関係・流れを視覚化する
- Mermaidの利用用途
  - `flowchart` : コンポーネント間の関係
  - `sequenceDiagram` : API、deploy、認証などの時系列
  - `stateDiagram-v2` : 状態遷移
  - `erDiagram` : テーブルのリレーション、データモデルの概念説明
  - `classDiagram` : クラス・オブジェクトの依存関係
  - `architecture-beta` : アーキテクチャ図

### 設計レビュー

- spec.mdが完成したら一度すべての内容を確認し、ブレインストーミングでユーザーと決めた仕様・設計に準拠しているかを確認する。
- ユーザーと会話されていない設計判断が必要な記述があればユーザーに確認する

## 2. 実装計画

`/superpowers:writing-plans` スキルを利用して、`spec.md` を実装計画に落とし込む。
実装計画は `agent-tasks/タスク名/task.md` にマークダウンで保存する。

- 各ステップのタスクはチェック可能な項目とし、完了・未完了がわかるようにする
- 各ステップに、正しく実装できているかを確認する手順(テストの追加・実行を含む)を含める
- `spec.md` で定義したテスト戦略を、どのステップでテストを書き・実行するかに落とし込む
- デプロイ手順の作成、ドキュメントの修正もスコープに含める
- git commitなど、コードベースの変更を確定する操作をタスクに含めるかどうかをユーザーに確認すること。特に指定がない場合はタスクに含めてはいけない
- デプロイ、ブランチのpushなど、既存環境への変更の適用はタスクに含めない

## 3. 設計・実装計画のレビュー

実装を開始する前に、`spec.md` と `task.md` をレビューする。
レビュー結果は `agent-tasks/タスク名/review.md` にマークダウンで保存する。
客観性を保つため、レビューは `spec.md` `task.md` を書いた本人とは別の sub agent に委ねること。

- レビュー観点
  - ドリフト検知: ユーザーとAIで brainstorming して決めた仕様・設計と食い違っていないか
  - 情報の正確性: Context7、web検索で公式の最新情報を確認し、内容の正確性をチェックする
  - 全体的な整合性: 新しい変更が、既存のアーキテクチャ、データモデル、API、命名規則、コンポーネントの役割分担と矛盾なく調和しているか
  - 根本解決と技術負債の回避: その場しのぎの修正になっていないか。複雑性を上げたり、将来的な技術負債を生んだりしていないか
  - 再利用性と共通化: 車輪の再発明を避け、既存の共通コンポーネントやユーティリティを適切に活用しているか
  - 破壊的変更の検知: リソースの強制置換など、既存の稼働中インフラを停止・破壊してしまう実装が含まれていないか
  - セキュリティと最小権限: IAMポリシーやセキュリティグループに不要な権限がついていないか
  - 将来への影響: 将来的な機能拡張やスケールアウトを不必要に妨げる設計になっていないか
- 修正項目をユーザーに報告
  - review.mdはユーザーがタスクのフローを確認しやすいように、冒頭に目次をつける
  - 修正の要否をstep by stepでユーザーに質問する。ユーザーが判断しやすいよう、質問には目的、経緯、トレードオフなどの背景情報を含める
- 重大な指摘があれば `spec.md` / `task.md` に差し戻し、合意が取れてから実装に進む

## 4. 実装

`/superpowers:subagent-driven-development` スキルを利用して `task.md` に沿って実装を進める。

- 一気に実装するか、ステップごとに人間によるレビューを挟むかを人間に選択させること
- メインのコンテキストを節約するため、sub agent、agent teamを積極的に利用すること
- 各ステップで、 `task.md` に定めたテストを書き・実行し、確認手順を満たしてから次へ進むこと
- 進捗に応じて完了項目をマークすること
- 追加の設計判断が必要になった場合はそのまま進めず、ユーザーに質問すること
- 設計・計画の変更が必要になった場合は、ユーザーの確認をとって `spec.md` 、 `task.md` を修正すること

## 5. 実装レビュー

実装が完了したら、品質ゲートとして以下を確認する。`spec.md` を書いた本人とは別の sub agent に委ねること。

- 正確性の実証: 対象層のテストを実行し、ログを確認して正しく動作していることを実証する。テストが失敗していたら4に戻る
- 仕様適合: `spec.md` 、 `task.md` の内容と実装が食い違っていないかを確認する
- 設計適合: 3のレビュー観点(根本解決・整合性・再利用性・セキュリティなど)を実装に対して再点検する
- 最終確認: 「スタッフエンジニアならこの変更を承認するか?」を自問し、承認できる水準であることを確認する

## 6. 重要な設計判断をドキュメントに残す

重要な設計判断を[MADR (Markdown Architectural Decision Records)](https://adr.github.io/madr/) を利用して、 `docs/adr/<TICKET_ID>_<TITLE>.md` に残す。

- 今回の修正において、重要と思われる設計判断を抽出し、どれをADRに残すかをユーザーと相談する
- テンプレートはfullとminimalの2パターン。内容に応じて選択する。
  - full: https://raw.githubusercontent.com/adr/madr/refs/tags/4.0.0/template/adr-template.md
  - minimal: https://raw.githubusercontent.com/adr/madr/refs/tags/4.0.0/template/adr-template-minimal.md
- ADRは日本語で記述する
- ADRのレビューとcommitはユーザーにゆだねる。

## 7. 教訓の抽出

ワークフロー内でユーザーから受けた指摘で、一般的に他のタスクにも適用すべきものを教訓として auto memory に残す。

- 教訓は本質的な学びとなるよう抽象化し、関連する既存メモリと結びつける
- auto memory を一度俯瞰し、必要であれば教訓の統合や廃止を行う
